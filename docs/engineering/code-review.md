## 代码审查（Code Review）设计说明

本技能基于 Matt Pocock 的双轴审查架构，针对单人本地开发体验做了无网络依赖的收敛。

### 核心设计哲学：双轴独立（Two Axes）
- **规范不能遮掩功能缺失**：漂亮的坏功能依然是 Bug；
- **功能不能纵容架构腐化**：跑通了但散发着浓烈坏味道的代码会破坏可维护性。

### 本地化改进：
1. **规格来源按顺序找**：作者在对话里给出的规格、需求或设计文档优先，其次是本地 `.agents/notes/proposed/` 与 `docs/` 里的同类文档。没有规格就写「no spec available」，Standards 轴照常跑，Spec 轴标未评；需要规格轴时，先用 `to-spec` 把讨论里已明确的需求收敛成规格再评。这是后续路线提示，审查本身不调用 `to-spec`、不写规格，也不从当前实现反推验收标准；需求还没定的时候，`to-spec` 也补不出来。
2. **坏味道基线内置**：内置 Martin Fowler 坏味道基线，项目未提供单独的 Lint/规范文件时也能给出架构反馈。项目自己的规则优先：先读 `AGENTS.md` 与编码规范文档，连别的工具生成的也算项目规则；它们没盖到的地方才回落到基线。
3. **范围自己定，先说清**：作者给了路径、基线或区间就照办；没给就从当前任务、已有计划规格、改动涉及的入口与调用关系推定，并在开头报告本次范围、依据、包含与排除、局限，先推进能确定的部分，不把追问当门槛。先分清是「审这次改动」还是「审当前项目/模块」：仓库有 Git 本身不代表要凑一个 diff，泛指项目时按入口和核心流程做当前状态审阅。已提交且工作区干净不等于没有改动，用任务相关的提交说明、涉及路径与测试拼出一组连贯变更，基线标 `inferred`，不默认只取 `HEAD`、最近 N 个或整仓，也不拿文件 mtime 当改动证据。目录没有 Git 时用 `rev-parse --is-inside-work-tree` 与 `--show-toplevel` 确认是否误入父仓，然后按当前状态审阅并标明覆盖范围；不 `git init`、不造假 diff、不断言新增或回归，没有基线就写 baseline unavailable，结论只对当前文件成立。
