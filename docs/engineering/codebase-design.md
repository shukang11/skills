## Codebase-Design 机制深度设计与工程原理

`codebase-design` 的核心使命是**对抗大模型写代码时的“复杂度膨胀熵增”**。

### 1. 为什么 AI 极容易写出“浅模块（Shallow Modules）”？

由于统计概率倾向，大模型非常习惯于“把一个长函数拆成 5 个小函数，分散在 3 个文件里”。表面上看代码变短了，但实质上：
- **认知负担爆炸**：阅读者必须在 3 个文件、5 个函数之间反复跳转才能理解整体逻辑；
- **接口大于实现**：每个小模块暴露的接口成本，远远超过了它内部完成的一点微小工作；
- **依赖蔓延**：底层的细节被原封不动地暴露给上层，形成了厚重的传递依赖链。

### 2. 深模块哲学（Deep Module Philosophy）

根据 John Ousterhout 的理论，模块的最佳形状是一个**倒 T 型（Deep Module）**：
- **横梁（Interface）极窄**：调用者只需要记住极少甚至唯一的 API；
- **竖立（Implementation）极深**：底层的脏活、累活、容错和边缘情况全部在深处闭环消化。

```text
浅模块 (Shallow - 差):            深模块 (Deep - 优):
┌───────────────────────────┐         ┌───────┐  <-- 极小极纯的 Public API
│   Overly Broad Interface  │         │  API  │
└───────────────────────────┘         └───┬───┘
            │                             │
    ┌───────┴───────┐             ┌───────┴───────┐
    │ Thin Impl (3L)│             │               │
    └───────────────┘             │  Deep & Rich  │
                                  │ Implementation│
                                  │ (Hidden Info) │
                                  │               │
                                  └───────────────┘
```

### 3. 与文档体系的自驱闭环

一个健康的单人代码库，其架构不是写死在历史 Commit 里的，而是沉淀在 `docs/` 和规范目录中的活文档（Living Documentation）。
通过将“文档感知”与“架构回写”作为 `codebase-design` 的内置守则，保证了 Agent 无论在何时启动，都能站在最新的架构高地上思考，而不是在杂乱的代码堆里盲人摸象。
