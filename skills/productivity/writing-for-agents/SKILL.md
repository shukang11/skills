# Writing for Agents

编写任何供 Agent 消费的文档（技能定义、`AGENTS.md`、规范文档）的元心法。
核心目标：**让 Agent 每次都做出同样正确的判定，而不是依赖随机的悟性。** 要做到这一点，靠的是意图、判据和可检验的收工条件，而不是把模型本来就会的做法逐步写出来。

## 两种负荷预算（The Two Loads）

你新增的每一份文档或指针，都在消耗两种预算之一：
- **上下文负荷（Context Load）**：每轮会话常驻消耗的 Token 和注意力（如 `AGENTS.md`、常驻技能描述）。无论是否触发都在扣减预算，因此常驻描述必须极度精简。
- **认知负荷（Cognitive Load）**：由人类判断何时选用哪个工具/文档的心智成本。

**指针原则（Context Pointers）**：
- 技能描述（Description）本质上是一个上下文指针；
- **首词触发（Front-load leading words）**：把最重要的触发动词和场景词置于开头；
- **一分支一触发**：不用同义词堆砌重复触发条件。

## 写什么、不写什么

**写**：
- **意图**：一句话说清要达到什么效果、为什么。
- **判据**：规则里有要判断的词（「重要的」「机械可判的」「行为变更时」），就同时给出判据。检验：两个 Agent 读到这条，会做出同样的判定吗？
- **收工检查**：可检验的完成条件，最好是一条命令或一个能核对的产物。
- **模型推断不出的约定**：项目特有的命名、路径、trailer、tag、门禁的精确格式。
- **产出格式**：报告结构、文件落点。

**不写**：模型已经掌握的通用方法论（常见排错手段清单、坏味道名录、TDD 教程），以及同义重复的触发词和长串「千万不要」。

**步骤只在两种情况下写**：顺序有讲究且模型猜不到；或者错一步代价很大（碰到人的工作区、不可逆操作）。能写成脚本的就写成脚本，技能只说「跑它，按它的输出判断」。

**只写原则不够**：没有判据和收工检查的原则就是口号。实测中，「宣称完成前派新会话核对」写得再清楚，压力下 6 次被跳过 6 次；同一件事交给脚本复核，9 次全部判对。

**删除测试**：逐段问一句，删掉这段，换一个能力强的模型来执行，结果会变吗？不会变的就删。

## 信息阶梯与渐进式披露（Information Hierarchy）

1. **主文件**：意图、判据、收工检查、产出格式，以及必须写的步骤；
2. **就地参考**：当场要查的定义、反例；
3. **披露参考**：低频的展开细节和边缘案例，拆到 `references/` 下的独立文件，用指针按需加载。

文档过长会稀释注意力；主文件只留每次执行都要用到的内容。

## 完成判定标准（Completion Criteria）

- **清晰性**：Agent 能否明确区分「已完成」与「未完成」？模糊的表述（如「梳理清楚了」）会引发过早完工。
- **高要求**：「列出所有修改的模块」比「给出一个变更清单」约束力更强。
- **可核对**：优先让完成条件指向别人能复核的产物（命令输出、测试、文件:行号），而不是 Agent 的自述。

## 引导词工程（Leading Words）

- 用 *tight*（紧凑的）、*red*（飘红的）这类高权重工程词，替代一段关于「快速、确定性、可验证」的长篇描述；
- **肯定式引导**：告诉 Agent 该怎么做，尽量少写「千万别怎么做」，否定句容易把禁止的行为拉进注意力。

## 附：`SKILL.md` 默认结构

```markdown
---
name: <kebab-case 技能名称>
description: "<首词前置的触发场景与功能描述，1-2 句>"
argument-hint: "<调用时需要用户提供的入参提示（可选）>"
---

# <技能标题>

<一句话：要达到什么效果，为什么>

## 判据
- <两个 Agent 读了会做同样判定的规则；含判断词的，同时给判据>

## 收工检查
- <可检验的完成条件，优先一条命令或可核对的产物>

## 产出
- <输出的章节结构、文件路径或格式>

## 步骤（可选：仅当顺序猜不到，或错一步代价很大）
1. <步骤> — 收工：<条件>
```
