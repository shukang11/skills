# 排错手册

主文件的判据怎么落地。红信号搭不出来、搭出来又慢又不稳、或最小化与溯源卡住时读。

## 搭红信号的载体（按推荐顺序）

1. **特定失败测试（Failing test）**：在触及该 Bug 的最小测试接缝处编写单测、集成测试或端到端测试。
2. **Curl / HTTP 脚本**：针对正在运行的本地开发服务器发起特定请求。
3. **CLI 调用**：带有固定 fixture 入参的命令行调用，将 stdout 与预期快照对比。
4. **无头浏览器脚本**：驱动 UI 并对 DOM / 控制台报错 / 网络请求做断言。
5. **重放真实捕获追踪（Replay a trace）**：将真实网络请求、载荷、事件日志保存至磁盘，隔离重放经过 Bug 路径。
6. **一次性 Harness（Throwaway harness）**：启动系统的最小子集（单个函数或模块，Mock 掉无关外部依赖）。
7. **属性 / 模糊测试循环（Fuzz loop）**：Bug 是「偶发错误输出」时，跑 1000 次随机入参捕获失败模式。
8. **二分脚手架（Bisection harness）**：Bug 是在两个版本间引入的，自动化启动并检查状态，配合 `git bisect run`。
9. **差分循环（Differential loop）**：相同输入跑在旧版本与新版本（或两套配置）上，对比输出 diff。
10. **用户交互验证（HITL）**：最后手段。必须人工交互时，向用户提供清晰的步骤清单并捕获其反馈。

## 收紧红信号

把它当作产品来打磨：

- **更快**：缓存初始配置，跳过不相干的初始化，缩小测试范围（秒级最佳）。
- **更锐利**：断言具体症状，而不仅仅是「没崩溃」。
- **更确定**：固定时间戳、固定随机种子、隔离文件系统与网络。

红信号的四项标准：能精准飘红（走实际 Bug 路径、捕获确切症状）、确定（每次结论一致）、秒级（不跑全量套件）、Agent 可独立运行（无需人工）。

## 最小化

确认飘红后，把复现场景收缩到**依然飘红的最小边界**：

- 逐一削减无关入参、调用链、配置项与前置步骤；
- 每削减一步，重跑一次红信号；
- 只保留触发 Bug 所必需的要素。

## 假设与因果溯源

基于最小复现场景找根因：

1. **形成具体假说**：「X 传入了空值导致 Y 越界」，而不是泛泛的「数据处理有问题」；
2. **观察因果链**：用日志插桩或二分代码，看数据在哪一步开始异常漂移；
3. **定位真正根因**：区分症状爆发点与错误产生点，不在爆发点打临时补丁。
