# Diagnosing Bugs

处理疑难 Bug 的严谨纪律。除非有明确依据，否则严禁跳过任何阶段。

在探索代码库时，优先阅读 `docs/`、`.agents/notes/` 或 `README` 中关于该模块的既有架构与规范说明，建立正确的模块心智模型。

## 敏感信息脱敏（Redact）

本技能要求展示命令、输出与捕获的工件。**必须优先对所有敏感凭证脱敏**：用 `<REDACTED>` 替代。
尽量基于环境变量执行循环，让凭证保留在环境中而不是输出中。若脱敏后的信息不足以诊断 Bug，请明确向用户说明并询问。

## Phase 1: 构建反馈闭环（Build a feedback loop）

**这是本技能最核心的灵魂。** 其他一切都是机械操作。
如果你拥有一个**紧凑且必定飘红的信号**（一个能精准捕获*此 Bug*的失败信号），你必然能找到根因；二分法、假设验证和插桩日志只是在消费这个信号。如果没有这个信号，盯再久代码也无济于事。

在此投入不成比例的精力。**要积极，要有创造力，拒绝放弃。**

### 构建反馈闭环的常见方式（按推荐优先级排列）

1. **特定失败测试（Failing test）**：在触及该 Bug 的最小测试接缝处编写单测、集成测试或端到端测试。
2. **Curl / HTTP 脚本**：针对正在运行的本地开发服务器发起特定请求。
3. **CLI 调用**：带有固定 fixture 入参的命令行调用，将 stdout 与预期快照对比。
4. **无头浏览器脚本**：驱动 UI 并对 DOM/控制台报错/网络请求做断言。
5. **重放真实捕获追踪（Replay a trace）**：将真实网络请求/载荷/事件日志保存至磁盘，隔离重放经过 Bug 路径。
6. **一次性 Harness（Throwaway harness）**：启动系统的最小子集（单个函数/模块，Mock 掉无关外部依赖）。
7. **属性/模糊测试循环（Fuzz loop）**：如果 Bug 是“偶发错误输出”，跑 1000 次随机入参捕获失败模式。
8. **二分脚手架（Bisection harness）**：如果 Bug 是在两个版本间引入的，自动化启动并检查状态，配合 `git bisect run`。
9. **差分循环（Differential loop）**：将相同输入跑在旧版本 vs 新版本（或两套配置）上，对比输出 diff。
10. **用户交互验证（HITL）**：最后手段。若必须人工交互，向用户提供清晰的步骤清单并捕获其反馈。

### 收紧闭环（Tighten the loop）

把该闭环当作产品来打磨：
- **更快**：缓存初始配置，跳过不相干的初始化，缩小测试范围（秒级响应最佳）。
- **信号更锐利**：断言具体症状，而不仅仅是“没崩溃”。
- **更确定**：固定时间戳、固定随机种子、隔离文件系统与网络。

### 阶段完成标准：一条必定飘红且秒级的单命令

Phase 1 结束的硬性标准是：你能够给出一行**已经实际运行过且可独立重复运行的单命令**，并且满足：
- [ ] **能精准飘红（Red-capable）**：能驱动实际 Bug 代码路径并捕获用户的确切症状。
- [ ] **确定性（Deterministic）**：每次运行结论一致。
- [ ] **极速（Fast）**：数秒内完成，绝不运行全量测试套件。
- [ ] **自动化可跑（Agent-runnable）**：无需人工干预即可运行。

**严禁在没有这行飘红命令之前，盯着代码臆测原因或尝试修改业务代码！**

## Phase 2: 复现与最小化（Reproduce + Minimise）

运行该闭环命令，确认捕获到用户描述的确切症状（而非周围其他不相干报错）。

### 最小化（Minimise）
一旦确认飘红，将复现场景收缩到**依然飘红的最小边界**：
- 逐一削减无关入参、调用链、配置项与前置步骤；
- 每削减一步，重新跑一次闭环命令；
- 只保留触发 Bug 所必需的核心要素。

## Phase 3: 假设、因果溯源与二分（Hypothesise, Trace & Bisect）

基于最小复现场景，探寻根本原因：
1. **形成具体假说**：“是因为 X 传入了空值导致 Y 越界”，而不是泛泛的“数据处理有问题”；
2. **观察因果链**：通过日志插桩或二分代码，观察数据是在哪一步发生异常漂移的；
3. **定位真正根因**：区分“症状爆发点”与“错误产生点”，防止在爆发点打临时补丁。

## Phase 4: 修复与验证变绿（Fix & Verify Green）

1. **精准修复**：实施针对根因的最小修复，严禁引入未经讨论的大面积重构；
2. **验证变绿**：运行 Phase 1 建立的单命令闭环，亲眼确认测试从**红**变为**绿**；
3. **清理临时脚手架**：移除排错过程中临时添加的调试日志与临时脚本。
