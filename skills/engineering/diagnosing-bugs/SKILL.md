# Diagnosing Bugs

先拿到一个只为这个 bug 飘红的信号，再动代码。有了它，定位只是在消费信号；没有它，盯多久代码都没用。在这一步上投入不成比例的精力，要积极、有创造力，不轻易放弃。

顺序固定：搭红信号 → 最小化 → 假设与溯源 → 修复变绿。前一步没完成不进下一步。

## 判据

- **先读既有说明**：动手前读 `docs/`、`.agents/notes/`、README 里关于该模块的架构与约定。
- **红信号**：一条实际跑过、可重复运行的单命令，走真实的 bug 路径，复现用户描述的那个症状，而不是旁边另一个报错。要求确定、秒级、无需人工。拿到它之前不改业务代码。
- **载体顺序**：测试接缝处的失败测试优先；需要人来操作是最后手段。
- **最小化**：确认飘红后，把复现收缩到依然飘红的最小边界，每削一步重跑一次。
- **根因**：区分症状爆发点和错误产生点，修产生点。修复最小，不夹带没讨论过的重构。
- **凭据**：命令和输出里的凭据写成 `<REDACTED>`，尽量让凭据留在环境变量里。脱敏后信息不够诊断时，向用户说明。

红信号搭不出来、搭出来又慢又不稳、或最小化与溯源卡住时，读 [references/playbook.md](references/playbook.md)：10 种载体、收紧手法、最小化与溯源的做法。

## 收工检查

- 红信号在修复前红、修复后绿，两次都实际跑过，输出摘要写在回复里。
- 红信号是测试的，把它留在修复提交里当回归测试：在父提交上红、在本提交上绿。spec-anchor 项目的周期审查会用 `fix-proof` 复核这一点。
- 红信号不是测试的，提交信息带 `Tested: <怎么验证的>`。
- 项目根 `AGENTS.md` 有修复提交约定（标题前缀、账本 trailer）的，按约定写。
- 排错用的临时日志与脚本已清掉。
