# Test-Driven Development (TDD)

TDD 是 Red → Green 的行为验证循环。本技能定义了高质量测试的标准、测试接缝的选择、需规避的反模式，以及循环执行的核心法则。

> **⚠️ 核心触发纪律（里程碑原则）**：
> 在日常编码和迭代开发过程中，**除非到达关键里程碑（Milestone）、一个完整原子特性的验收节点，或者用户明确下达执行测试指令，否则 Agent 不要擅自、主动频繁地跑完整体测试套件**。避免无意义的等待与上下文开销，专注于逻辑构建。

## 什么是好的测试？

好的测试应当通过**公共接口（Public Interface）**验证系统行为，而不是依赖内部实现细节。
- 代码的内部实现可以彻底重构，但测试用例不应轻易失效。
- 好的测试读起来应该像一份活的规格说明书（例如：`"user can checkout with valid cart"`）。

## 测试接缝（Seams）：测试应该写在哪里？

**接缝（Seam）**是进行测试的公共边界：即在不侵入系统内部的情况下观察系统行为的接口。
- **只在事先确认的接缝处编写测试**。
- 严禁针对模块私有方法、内部临时状态编写脆性测试。
- 遇到架构与接口形态存疑时，协同参考 `codebase-design` 的深模块理念。

## 常见反模式（Anti-patterns）

1. **与实现过度耦合（Implementation-coupled）**：
   - 过度 Mock 内部协作者、测试私有方法、或通过旁路直接刺探私有状态。坏味道体现为：代码逻辑重构但外部行为未变，测试却挂了一大片。
2. **同义反复/套套逻辑（Tautological）**：
   - 断言重新计算了业务代码相同的算法（例如：`expect(add(a, b)).toBe(a + b)`），导致测试永远为真，失去了独立验证意义。预期值必须来源于独立的真源（固定的常量字面量、规范计算样本）。
3. **横向切片（Horizontal slicing）**：
   - 一口气写完所有测试，再一口气写所有实现。这会导致基于“脑补的契约”写出大量僵尸测试。应当坚持**纵向切片（Vertical slices）**：一次一个端到端行为切片。

## 循环执行规则

- **Red before Green**：先写出可复现失败的测试，接着编写最少量的代码使其通过。不提前预测未来需求，不写过度防御代码。
- **一次一个切片**：一次只关注一个接缝、一个测试用例、一个最小实现。
- **里程碑集中验收**：单个微切片完成后快速推进，到达阶段性里程碑时，再统一进行验证与回归。
