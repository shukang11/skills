# 审计模型

## 核心问题

审计时始终围绕一个问题：

> 零上下文 Agent 能否只凭仓库内信息，安全完成真实任务？

不要用文件数量、标题完整度或 Markdown 美观度代替这个判断。

## 八个审计维度

### 1. 定位

- 根入口能否说明项目用途和边界。
- 用户意图能否映射到明确的模块或事实来源。
- 是否必须先全库搜索才知道从哪里开始。

### 2. 权威性

- 每类动态事实是否只有一个权威来源。
- 汇总页是否复制了会漂移的状态。
- 冲突时是否明确哪一份优先。

### 3. 范围

- 工作流是否定义默认扫描和修改范围。
- Agent 能否避免读取无关历史、模块或外部数据。
- 用户限定范围时是否有明确覆盖规则。

### 4. 安全

- 不可推断字段是否列明。
- 状态、发布、删除、迁移等高风险动作是否需要确认。
- 禁止路径是否在危险动作附近也有护栏。

### 5. 可执行性

- 工作流是否有输入、输出、步骤和验收。
- 模板能否独立生成完整对象。
- Agent 能否产出实际结果，而不只是复述规则。

### 6. 验证

- 是否有可复制运行的命令。
- 是否说明通过标准、能力边界和失败处理。
- 文档是否夸大检查工具覆盖范围。

### 7. 演进

- 决策记录是否与当前事实分离。
- 废弃内容是否变成不可执行墓碑。
- 目录或模块变化时，引用和地图是否同步更新。

### 8. 鲁棒性

- 普通 Agent 是否成功。
- 较轻量 Agent 跳读、乱序或扩读时是否仍安全。
- 关键护栏是否只存在于一个容易被跳过的入口。

## 证据要求

每个 P0/P1 问题至少包含：

- 触发它的真实任务。
- 文件路径与行号或命令输出。
- Agent 实际行为，而非推测。
- 可能造成的具体后果。
- 应在哪一层解决。

没有证据时标为假设，不直接改结构。

## 分级

- **P0**：可能产生不可逆或高代价错误。
- **P1**：任务无法独立完成或必须猜测。
- **P2**：可以完成，但上下文、时间或输出浪费明显。
- **P3**：纯表达偏好。

先清零 P0，再处理 P1。P2 必须有真实成本证据；不要为消灭所有 P3 无限扩写文档。

## 出口归属

每条建议必须落在一个出口；不存在“没有出口”的建议。

- **出口① 造眼睛**：错误能被会跑的检查捕获（lint / test / CI / 只读守卫）。
- **出口② 收窄路**：错误选项在默认路径上消失（模板 / 目录约定 / 脚手架 / 唯一写法）。
- **出口③ 人侧记账**：无法机械验证，明确划给“必须人来”，并写清落在哪个动作上。

门禁要求的是“必须有出口”，不是“必须是出口①”。把不可机械验证的项硬塞成坏检查是反效果：只增加噪声，并制造“已验证”的假象，应改记出口③。

## 建议指标

不要设统一硬阈值；记录基线与整改后的变化：

- 到第一个正确事实文件的时间和跳转数。
- 必读文件与实际读取文件的差值。
- 无关文件读取比例。
- 前置澄清问题数量。
- 未经证据提出的修改数量。
- 验证失败后能否自行定位处理入口。
- 普通 Agent 与较轻量 Agent 的安全通过率。
